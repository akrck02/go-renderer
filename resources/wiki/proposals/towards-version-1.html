1. Go Renderer towards 1.0

Status: building · Author’s approval: proposal ☑ (2026-10-22, with the decisions below) plan ☑ (2026-10-22, “Si”)

Why

Go Renderer is an educational experiment at v0.2.0. Games and libraries (Go UI, go-engine) already build on it, so a version they can trust would help them. Today nothing promises that:

  • Little is checked automatically. Until this branch, no workflow ran the tests. The OpenGL scene renderer is never checked by a program: its tests skip without a display, and a frame that came out wrong would pass.
  • Stub backends. software, vulkan and webgpu are hand-written beginnings of the immediate-mode contract: every call returns “Graphics API not implemented yet!”. A newcomer cannot tell that from the folder list.
  • Metal is tried by hand. It runs on the author’s Mac only, and newer SDKs (macOS 27) deprecate MTLStorageModeManaged, which its textures use.
  • No releases since v0.2.0. Paths, strokes, fullscreen, pads and DrawOver landed on main since; nothing says what may break between versions.
  • AI-written parts are pending review. The README says so; a 1.0 should not.
  • Central packages are thinly tested. Coverage of windowloop is 6 %, graphics 46 % and scene 50 %.

Out of scope

  • New features (fills of paths, areas in Metal and the browser): 1.0 is about trust, not reach.
  • Building Android and the 3DS on every push: they need the NDK and a TinyGo fork; go-engine’s proposal 14 covers them for the whole family.
  • Changing the hand-written Renderer contract or backends without the author.

Decisions

The author’s answers (2026-10-22):

  1. The stub backends (software, vulkan, webgpu) stay, to be built later. The docs say so, and every function returns an error that says it is not implemented, with a code.
  2. What 1.0 promises: every package. So every package first passes an audit against the author’s guidelines (llm-guidelines), and its API is made simple and efficient.
  3. Frames in CI: Mesa’s software driver under Xvfb.
  4. The review: the author reviews every AI-written part once the audit is done and what it asks is simplified or rewritten.
  5. The Mac: a MacBook Air M4, where Metal has been tried so far.

And above all: performance and a simple API (developer experience) are imperative. Every change of this proposal is weighed by both: an API a newcomer reads in minutes, and frames that cost no more than today, measured.

Design

One error package. Go Renderer has no error codes today (33 files build errors from text). A small package, failure as in go-engine (Define, Wrap, codes compared with errors.Is), is shared by every package; each declares its codes in its own errors.go. The stub backends return <backend>.not-implemented.

The audit, before any rewrite. A reviewer reads each package against llm-guidelines (names, size of functions, early returns, error codes, generic names, nothing allocated per frame, comments, tests that prove behaviour, docs) and against the two imperatives: is the API the smallest that does the job, and what does a frame cost. Its findings go in one document, docs/proposals/1-audit.md, package by package, each finding with a severity and what to do. Nothing is changed while auditing: the author reads the findings and the plan of each package before it is rewritten.

Measured performance. Before rewriting, the benchmarks that exist (34) are run and kept as a baseline, with new ones where a frame’s hot path has none (the scene renderer’s frame, a 2D list of three hundred controls, a pad’s reading). A change that makes a frame slower or allocate more does not merge.

Frames compared in CI. A test draws the sample island and a 2D list under Xvfb with Mesa (llvmpipe) and compares them with reference pictures in the repository, within a tolerance; a pass broken on purpose fails it. The CI installs Mesa and runs it under xvfb-run.

Metal. The AI-written Metal renderers use MTLStorageModeShared where Managed is deprecated (it does nothing on Apple silicon); the author’s hand-written stubs are left as they are. The release checklist names the MacBook Air M4.

1.0’s promise. A page, docs/6-project/3-version-1.md, says that every package is stable from 1.0: what that means (no breaking change without a major version), how a change is deprecated first, and that releases carry notes (go-engine’s proposal 14).
