4. Emoji on any Android

Status: approved, to build · Author’s approval: proposal ☑ plan ☑ (through the organizer, 2026-10-27)

Why

On Android the overlay reads colour emoji from the system’s font files, and it can only read one kind of them: CBDT, where each emoji is a PNG picture. Android 13 moved its own emoji to COLRv1, where each emoji is a vector drawing with gradients, and kept a CBDT copy, NotoColorEmojiLegacy.ttf, for programs like this one. On the Android 14 emulator that copy is there, and a chat made with Go UI draws 👍 in colour.

A Pixel 6 Pro on Android 17 draws ? instead: a recent Android, and phones whose maker ships its own emoji font, carry no CBDT file the overlay can read. Every emoji turns into a question mark, in every program built with go-renderer, and nothing tells the program why.

Out of scope

  • Sequences joined by U+200D (a family, a skin tone, most flags): shown as their parts, as on every platform today. Android’s canvas could draw them later; the seam below allows it.
  • Reading COLRv1 in Go, for desktops whose Noto Color Emoji is COLRv1 too: compared below, and left for a later proposal if wanted.
  • Typing emoji in Go UI’s own fields on Android: android/java/TextInput.java is someone else’s work in progress, and this proposal does not touch it.

Design

The idea: let Android draw what it can draw

Proposal 3 did this for the browser: the browser has the system’s emoji, so it paints each one into a small canvas, and Go reads the pixels back once. Android’s own Canvas can do the same. A Paint with the text size, Canvas.drawText into a Bitmap, and Paint.getFontMetrics and measureText for where it sits. Android draws whatever its emoji font is (COLRv1, CBDT, a maker’s own), so this works on every phone, now and after the next format change.

Where it plugs in

Proposal 3 left a single seam: emojiFont asks an emojiSource for a character’s picture at a size, and both the painter and the Measurer go through it. Nothing above it changes.

  • A chain of sources. On Android the source becomes two in order: the font files first (today’s code, cheap, no Java), then the platform. The second is asked only for a character the first has no picture of (R3).
  • A generic hook in the overlay. The overlay cannot call Java: it knows nothing of Android, and android already imports it through gles. So the overlay offers a function a platform sets once, at start, before the first frame:
  // UseSystemEmoji makes the overlay ask the platform to draw an emoji no font file has.
  overlay.UseSystemEmoji(func(character rune, pixels int) (picture image.Image, left, top, advance float32, found bool))

It is named for what it does on any platform, not for Android. The desktop and the browser never set it (R6).

  • The Android side (android/): a new Java file, android/java/EmojiPicture.java, compiled and loaded like ScreenReader.java, with one static method. It takes the character and the size and returns the ARGB pixels with the four measures. A small C function calls it through JNI and attaches the calling thread to the Java machine when needed, since the overlay draws on the GL thread. Go turns the pixels into an image.NRGBA (Android’s are premultiplied: they are divided back). The android package sets the hook when the activity starts.
  • Telling a monochrome letter from an emoji. Android can draw a character in a plain font when its emoji font lacks it. As in the browser, the character is drawn in two colours; a colour emoji keeps its own colours, a letter follows the fill, and then there is no picture (R5).

Why not read COLRv1 in Go

Android draws it COLRv1 read in Go
Works on every Android, any emoji font, future formats only phones whose emoji font is COLRv1
Size of the work a Java method, a C call, a Go hook; about 200 lines a paint graph (gradients, transforms, blending) and a rasteriser for it; well over 1,500 lines
Same look as the phone’s other apps yes, by construction close, if every paint is right
Also helps the desktop no yes, where the Noto Color Emoji is COLRv1
Calls Java once per emoji and size never

Reading COLRv1 would teach the most, but it is a large project for a narrower result. Bundling a CBDT emoji font in each app (about 10 MB, and out of date against the phone) is not taken either.

Reproduced without the phone

Deploy-manager reproduced the ? on the Android 14 emulator on 2026-10-27: with NotoColorEmojiLegacy.ttf moved out of /system/fonts, only the COLRv1 NotoColorEmoji.ttf is left (tables COLR, CPAL and glyf, no CBDT), and a chat’s preview shows “recibido ? te leo.”. With the file back, it shows 👍. R1’s capture is taken on that emulator with the file moved out; the author confirms on the Pixel afterwards.

That check found a small slip too: colourEmojiFiles takes any file whose name has “emoji” and “color”, whatever its extension, so a file renamed .ttf.hidden is still read. It should take font files only (.ttf, .otf, .ttc, .otc), as isFontFile does.

Result

Built on feature/android-emoji, one commit per task, not pushed. gofmt, go vet and go test ./... pass; the android package builds for android/arm64 and android/amd64, and EmojiPicture.java compiles against android-36.

On the Android 14 emulator, a small Go UI program with 😀 👍 🚀 ❤️ at 16, 32 and 48 pixels draws them in colour both with NotoColorEmojiLegacy.ttf in place and with it moved out of /system/fonts (R1; docs/images/android-emoji-*.png).

What differs from the plan:

  • No unpremultiplying in Go. Bitmap.getPixels already gives straight (not premultiplied) colours, so Go only reorders ARGB into image.NRGBA.
  • The hook is set in goStartMain, before main runs, not in Run: a program may measure text before its window starts, and an emoji looked for once is not looked for again.
  • The tool must carry the class. go-ui-apk compiles the java.Sources of the go-renderer it was built with. Built from go-ui-android, whose go.mod points at ../go-renderer, it leaves EmojiPicture out and the phone keeps its question marks. Until this branch is merged, build the tool against this worktree (go build -modfile with the replace changed).

Not tested: a real phone (the author’s Pixel confirms after T6), and the arm64 build on a device.
