3. Emoji in the browser

Status: done, pending review · Author’s approval: proposal ☑ (2026-10-27) plan ☑ (2026-10-27)

Why

On Android and the desktop the overlay draws emoji in colour, read from the system’s colour emoji font. In a browser, a WebAssembly program cannot read the system’s fonts, so every emoji is drawn as ?: drawable() in opengl/overlay/layout.go swaps each character no font has for a question mark. The same goes for Chinese, Arabic and every other script the Go fonts lack.

A program built for both platforms then shows two different texts. A chat page made with Go UI (LLM-CP’s llmcp-chat) shows a message sent as “emoji test 😀👍” as “emoji test ??”. The text itself arrives intact; only the drawing loses it.

Out of scope

  • Sequences joined by U+200D (a family, a skin tone, most flags of more than two letters): they show as their parts, as on the other platforms today.
  • Other scripts (Chinese, Arabic) in the browser. The same idea would serve them. They are a second proposal if wanted, so this one stays small.
  • Typing emoji in Go UI’s own text field in a browser. Go UI’s pages type in a plain HTML field today. Typing on Android is someone else’s work in progress (android/java/TextInput.java).

Design

Let the browser draw each emoji. The browser has the system’s emoji font, so it can paint an emoji into a small 2D canvas. The program then reads that canvas’s pixels back into Go as an image.Image, made once per character and size. That picture enters the existing path: the picture atlas, in the same draw call as the text, faded as the text is. Only where the picture comes from changes.

There is a single seam. The painter (drawing.go) and the Measurer both ask fonts.colourFor, which asks emojiFont.glyph. So measuring and drawing agree by construction (R2), and nothing above the overlay changes: Go UI, its Measurer and the backends stay as they are.

  • emojiFont keeps what it does today: the cache of glyphs by character and size, and the mutex. What it loses is reading the font files: it asks an emojiSource for a character’s picture and metrics at a size, and the font-file reading moves behind that source.
  • The font files’ source (emoji_files.go, every build but js && wasm) is today’s code, moved as it is: colourEmojiFiles, parseColourFont, the scaling.
  • The browser’s source (emoji_browser.go, js && wasm) draws on an OffscreenCanvas (or a <canvas> when there is none). It sets the font to the systems’ emoji families (Apple Color Emoji, Segoe UI Emoji, Noto Color Emoji) at the size in pixels. measureText gives the advance and the ascent; fillText and getImageData give the pixels as an image.NRGBA. A canvas left empty means the system has no picture of the character, so no glyph. So does one the browser draws in the fill’s colour: it is drawn twice, in two colours, and a colour emoji keeps its own. Where there is no canvas at all (Node), the font files are read, as on other systems; with none in reach, the text keeps its ? (R5). Changed while building: the plan had no source there, but Node can read files, and the overlay’s tests run in it.
  • fallback.go picks the source when it makes the emojiFont: the browser’s under js && wasm, the files’ elsewhere. Fonts.Folders keeps its meaning for the files’ source; in a browser it is ignored, and the docs say so.

Not taken:

  • Ship a colour emoji font with the page (Noto Color Emoji, about 10 MB): a heavy download for every page, and its emoji would look unlike the system’s own.
  • Draw the text with HTML over the canvas: it would leave the overlay’s single draw call, and break clipping, fading and layering.
  • Ask the browser for every missing character, not only emoji: it would serve Chinese and Arabic too, but it changes how all fallback text is drawn; left for its own proposal.
